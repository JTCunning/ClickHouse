# A/B plan: write the result of `timeSeriesGroupArray` straight into its typed columns
**Experiment:** ../reports/2026-11-21-ts-group-array-result-copy.md · **Branch:** `lilred-perf-ts-group-array-result-copy` @ `aea89aafdf0b` (base master `521c4bcb7b94`) · **Task:** 2026-11-20-scout-write-timeseriesgrouparrays-resu · **Outbox:** issue #23 (`ready-to-build`)
**Claim:** the samples-table merge path of `TimeSeries` gets cheaper per sample: `timeseries_group_array.xml`'s `FINAL` read −20..−50%, its two result `GROUP BY`s −10..−30%, its `optimize_on_insert` `INSERT` −10..−25%, and the CPU of an `OPTIMIZE FINAL` of 8 samples-table parts −8..−20%; the `-State` and no-`FINAL` controls flat; merged rows identical.
**Evidence so far:**
- emulated by subtraction on master `521c4bcb7b94`, 2 vCPU, `max_threads = 1` (the change is inside an aggregate function, so no SQL emulation of B exists): the result step costs about 19 ns/sample (`timeSeriesGroupArray` − `-State`: 180 ms per 9.6M samples, 192 ms per 10M); `FINAL` minus the plain read is 205 ms per 9.6M samples, of which the result step is ~165–180 ms; in CPU profiles `insertResultInto` is 24–29% of the `INSERT` and 15–26% of a samples-table merge (85 ns/sample of merge CPU). The branch keeps a 1–2 ns/sample copy. Predicted ranges are 0.4×–1× of these (emulation skill §7).
- 2026-11-21 dry run on master `521c4bcb7b94` (`bench/ts-group-array-result/smoke-2026-11-21.txt`): the merge kit ran end to end as A/A (4 rounds per server, 20,000 series, 4.8M samples): 1 part after each merge, merge CPU 408 vs 394 ms (−3.2%, noise), merged-row hashes identical; the revised perf XML runs on master with each query under 0.6 s at one thread. Direction can't be dry-run (code inside a function).
- Unproven: the size on 16 cores and on CI's perf hosts; whether the residual copy is as cheap as assumed; the ingest end-to-end effect (not a target).

## Builds

## Machine

## Data
- Perf XML: generated by its own `fill_query`s (9.6M samples as 40,000 series × 4 rows × 60 samples; 10M one-sample rows; the same 9.6M as 4 unmerged `AggregatingMergeTree` parts).
- Merge: `bench/ts-group-array-result/gen.sh` (default `TimeSeries` table, merges stopped on its samples and recent samples tables, ROUNDS = 8 inserts of SERIES series × 30 samples 15 s apart, one hourly bucket, half counters and half 3-decimal gauges). `ab/merge_ab.sh` passes one `T0` to both servers so the data is identical. Size: `SERIES=80000` (19.2M samples, about 55 MiB per table on disk).

## Method
- Perf XML (T1–T4, G1, G2): `tests/performance/scripts/perf.py --runs 13` from B's tree against both servers, then `compare_perf_tsv.py` with its defaults, as for items 1–3. G3 the same way.
- T5: start A and B with `bench/ts-group-array-result/ab/server.sh` (its `config.xml.in` has `part_log`, which the kit reads): `CH=<A binary> DATA=<dir> ab/server.sh start A 9001`, `CH=<B binary> DATA=<dir> ab/server.sh start B 9002`. Then `CH=<A binary> PORTS="9001 9002" N=15 SERIES=80000 ab/merge_ab.sh > ab/merge-<date>.jsonl` and `ab/summarize.py ab/merge-<date>.jsonl`. The arm order rotates per round; each round regenerates the table on that server.
- Report CPU next to wall time for every target (perf-lab §7): `perf.py` gives both; T5's `merge_cpu_ms` and `merge_ms` come from `part_log`.
